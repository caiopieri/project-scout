# Security Definition of Done

Use this checklist whenever a change touches database access, authentication, external input, payments, or mobile code.

## Marco 2 — Banco e Domínio

- [x] Every table in the exposed `public` schema has RLS enabled.
- [x] `anon` has no table privileges in the internal MVP.
- [x] `authenticated` can modify only private user records, constrained by `USING` and `WITH CHECK` ownership policies.
- [x] Shared marketplace data is read-only for `authenticated` and writable only by `service_role` workers.
- [x] `service_role` is documented as server/worker-only and must never be exposed to the frontend.
- [x] Test coverage verifies cross-user project and action isolation, denied anonymous marketplace reads, and authorized service-role writes.
- [x] A local migration reset and live PostgreSQL integration suite have passed after the current migration.

## Remaining controls for later milestones

- Remote Cloudflare secrets are provisioned for the privacy Worker. User-facing `/api/*` routes stay disabled in production until rate limiting is implemented.
- Any new table, view, function, or storage policy must be reviewed for explicit grants, RLS, and service-role exposure before release.

## F0 — Observation events and collector health

- [x] Event and health payloads are schema-validated before crossing the domain boundary.
- [x] PostgreSQL constrains event types, subject identity, ingestion layers, completeness ranges and JSON shapes.
- [x] Event deduplication is enforced by `(source_id, dedupe_key)`.
- [x] Both internal tables have RLS enabled and no `anon` or `authenticated` privileges.
- [x] Only `service_role` can read or mutate raw observation events and collector telemetry.
- [x] A reset from zero and live PostgreSQL tests verify constraints, deduplication and denied authenticated access.
- [x] Worker completion and event producers use server-only credentials, validated inputs and transactional persistence.
- [x] Degraded connector failures persist bounded health records containing only stable internal codes, never third-party payloads.
- [x] Valuation lifecycle reads are server-side only, validate source/listing IDs and event rows at the Supabase boundary, and never expose raw observation events to the browser.

## Marco 3 — Auth and hostile project input

- [x] Browser authentication uses Supabase Auth; project endpoints require a Bearer token.
- [x] The Worker validates the token with Supabase Auth and derives the owner from the session; request payloads contain no trusted `userId`.
- [x] The same user JWT is forwarded to PostgREST, preserving RLS. `service_role` is absent from project CRUD.
- [x] API body, path ID, interpretation output, criteria and database response shapes are validated with shared Zod schemas.
- [x] Provider/model/rule/timestamp metadata is generated by the Worker and cannot be forged by the browser.
- [x] Cross-user read and mutation attempts are covered by repository, Worker and live RLS tests.
- [x] Deleted projects are hidden by default; forbidden and nonexistent reads are both 404.
- [x] Logs contain no JWT, password, anon/service key or request body.
- [ ] Rate limiting is not yet required for the internal local-only MVP; it becomes mandatory before remote exposure.

## Marco 4 — Collection tasks and privileged workers

- [x] Collection requests require a validated idempotency key and an active project owned by `auth.uid()`.
- [x] Authenticated users cannot directly insert/update/delete `collection_runs`; narrow RPCs own request/queued transitions.
- [x] Queue messages are schema-validated and contain no owner, criteria, provider, token or listing payload.
- [x] The consumer reloads canonical criteria and atomically claims work with a bounded lease.
- [x] Only the queue consumer uses `service_role`; browser and user-request repositories continue with the user JWT.
- [x] Connector failures have safe stable codes and transient/permanent classification; logs do not include task bodies or secrets.
- [x] Cross-user isolation, blocked direct mutation, service-role claim, redelivery and retry exhaustion are tested.
- [x] Production queue resources and Worker secrets are provisioned without exposing `service_role` to the frontend.
- [ ] DLQ/alerts and rate limiting remain required before enabling production `/api/*` routes.

## Marco 5 — Official eBay external input and credentials

- [x] Official API mode is an explicit server-side opt-in; mock remains the default.
- [x] Client secret and application tokens never enter browser packages, queue payloads, PostgreSQL, KV or logs.
- [x] OAuth, search and detail responses are JSON-validated before crossing the connector boundary.
- [x] Timeouts/retries are bounded; permanent and transient failures use stable internal codes.
- [x] Third-party error text and response bodies are not persisted or logged.
- [x] eBay unauthorized, rate-limit, payload and pagination failures map to stable semantic health states without retaining provider text.
- [x] Production eBay wiring fails closed when the global rate-limit policy or atomic `EBAY_RATE_LIMITER` Durable Object binding is missing.
- [x] Collection and analysis queue consumers route exhausted messages to explicit DLQs.
- [ ] Collection DLQ alerting and replay/retention procedure remain pending; the account-deletion queue stays without a DLQ until its privacy-retention policy is reviewed.
- [x] Atomic reservation across independent Worker isolates is serialized by the Production Durable Object; effective eBay quota confirmation remains pending before continuous Production collection.
- [x] Marketplace ID and connector mode are runtime-validated against a narrow allow-list.
- [x] Tests cover token caching, authorization refresh, rate limiting, malformed payloads, permanent failures and Worker wiring.
- [x] Local setup hides the Client Secret, requires gitignore protection, rejects symlink targets and atomically writes `.dev.vars` with mode `0600`.
- [x] Portal opening uses a fixed URL and argument arrays without shell interpolation; tests never launch a browser or use real credentials.
- [x] Sandbox credentials were configured privately and live OAuth/search connectivity was verified without logging secrets.
- [x] Non-eBay remote Wrangler secrets were provisioned; collection remains explicitly in mock mode.
- [x] Production application OAuth/Browse credentials were configured as Worker secrets and live connectivity was verified without logging secrets or tokens.
- [x] Live execution is capped at one search plus five details; retries consume the same six-request adapter budget.
- [x] Optional eBay request telemetry is sanitized, excludes URL/token/body data, and observer failures cannot alter collection behavior.
- [x] The manual Production probe fails closed without a 64-hex server secret, validates its body and persists no result; its temporary secret was removed after the live test.

## Marco 6 — Normalized ingestion and raw objects

- [x] Every collected record is schema-validated before normalization and persistence.
- [x] Raw JSON is canonicalized and content-addressed; PostgreSQL stores no large raw payload.
- [x] The ingestion RPC is fixed-search-path, uses no dynamic SQL and is executable only by `service_role`.
- [x] Authenticated execution of the ingestion RPC is denied by an integration test.
- [x] External ID/hash redelivery is idempotent and does not duplicate snapshots or price history.
- [x] R2/database failures are classified transient; invalid normalized records are permanent.
- [x] Secrets, tokens and third-party response bodies are absent from logs and queue messages.
- [x] Isolated remote R2 buckets and collection/deletion queues are bound to the production Worker.
- [ ] Bucket lifecycle policies and DLQ/alerts remain pending.

## Marco 6.1 — eBay Production privacy gate

- [x] The application does not claim the no-persistence exemption.
- [x] GET uses an exact configured endpoint/token and returns JSON only.
- [x] POST is size-limited, schema-validated and signature-verified before enqueue.
- [x] Queue publication failure returns an error so eBay can redeliver.
- [x] PostgreSQL audit excludes eBay account identifiers and is service-role-only.
- [x] R2 objects are removed before relational finalization; retries are idempotent.
- [x] Raw object keys use a keyed HMAC seller prefix for orphan cleanup.
- [x] Public Worker, remote Supabase/R2/Queue/KV bindings and server-only secrets are deployed.
- [x] The public GET challenge was independently recomputed and matched.
- [x] User-facing `/api/*` routes are disabled in production pending rate limiting.
- [x] The eBay portal accepted the alert email, exact endpoint and token; signed POST delivery, durable queueing and database completion were live-verified.

## Marco 7 — Textual analysis

- [x] Listing title, description and condition are bounded and schema-validated as hostile input.
- [x] Queue messages contain only a versioned analysis-run UUID; no listing text, user data or secrets.
- [x] Analysis output is strict, capped and rejects defect references outside the same result.
- [x] Analysis lifecycle RPCs use fixed search paths and are executable only by `service_role`.
- [x] Input-hash/model/prompt idempotency and atomic lease claims protect redelivery.
- [x] Authenticated users cannot invoke analysis mutation RPCs or directly write analysis rows.
- [x] Deterministic rules treat prompt-like listing text as data and record unknowns/limitations.
- [ ] Live LLM data processing, privacy terms, timeouts and provider quotas remain unreviewed because no live provider is implemented.
- [ ] Production analysis Queue, DLQ/alerts and deployment remain pending.

## F4 — Assisted collector maintenance

- [x] F4.1 failure classification is schema-validated, deterministic and does
      not expose provider messages, secrets or raw payloads.
- [x] Auth and parser failures never receive automatic retry permission;
      network/proxy retries have an explicit bounded limit.
- [x] F4.2 proposals are strict, connector-scoped, human-approved and
      non-executable; shell, patch bodies, secrets and lifecycle escalation are
      rejected before proposal creation.
- [x] Repair proposal history is schema-validated at the PostgreSQL adapter
      boundary, isolated by RLS, and writable/readable only by `service_role`;
      live tests cover service-role access and denied `anon`/`authenticated`
      access.
- [x] Sandbox replay requires explicit approval, never accepts production
      environment, bounds canary/budget, and converts malformed or failed
      replay into a non-executable `ROLLED_BACK` result without exposing the
      callback error.
- [x] Sandbox result history is schema-validated at the PostgreSQL adapter
      boundary, isolated by RLS, and writable/readable only by `service_role`;
      live tests cover service-role access and denied `anon`/`authenticated`
      access.

## F5.1 — Read-only auction lot intelligence

- [x] Electronic lot input, cost policy and dossier are strict Zod contracts;
      unknown action fields and non-electronic categories are rejected.
- [x] Lot evaluation is deterministic and read-only; missing market evidence
      or condition prevents `SHORTLIST` and raises uncertainty.
- [ ] Auction connectors, edital ingestion, live monitoring and legal/tax
      assumptions remain pending separate review and human gates.

- [x] Local auction documents and claims are strict, hash-shaped, lot-scoped
      and conflict-visible; action fields are rejected and no document content
      is sent to an LLM.
- [x] Auction monitoring is fixture-only, deterministic and read-only; event
      deduplication and alerts never trigger polling, bids, payments or other
      external actions.

## F1 — Multi-source connectors

- [x] eBay, Mercado Livre and Xianyu source manifests are validated and declare
      primary layer, disabled fallbacks, limits and semantic health states.
- [x] Mercado Livre official API payloads require server-side credentials and
      pass shared schema validation; fixtures exercise the path without network.
- [x] Mercado Livre live routing is opt-in only with explicit production mode and
      server-side access or refresh credentials; PKCE is used by the OAuth
      bootstrap, refresh is bounded/coalesced after `401` only, and `403` policy
      denials never consume refresh tokens or reach the frontend.
- [x] Mercado Livre OAuth bootstrap validates the exact HTTPS redirect and
      state plus PKCE, exchanges the authorization code from the local CLI,
      writes tokens atomically with mode `0600`, and the public callback never
      renders tokens.
- [ ] Mercado Livre live search remains pending external policy/permission
      validation; the observed `403` path is fail-closed and does not rotate
      refresh tokens.
- [x] Xianyu has no private-endpoint, CAPTCHA-bypass or unauthorized live path;
      its fixture connector and unavailable mode fail closed.
- [x] Source routing and generic normalization reject unknown sources and keep
      cross-source merge authorization disabled.

## F2 — Search intelligence

- [x] Query families and learned terms are schema-validated; candidate terms
      require explicit evidence and acceptance before execution.
- [x] Families are persisted per collection run and term observations are
      owner-readable with RLS; worker collection writes are idempotent.
- [x] Authenticated owners can change only observation `status` through the
      review route; cross-tenant reads and non-status writes are denied by RLS
      and column privilege.
- [x] Deterministic triage decisions remain read-only; human review uses an
      owner-checked fixed-search-path RPC, while direct authenticated table
      inserts are revoked and only `status` is mutable on existing reviews.
- [x] Triage review tests cover the owner path, cross-tenant denial, invalid
      status validation and non-status write denial after a live migration.
- [x] Cheap screening treats listing content as hostile data and routes
      suspicious prices or ambiguous identity to review.
- [x] Product identity outputs `mergeEligible=false`; equal titles or prices
      never authorize cross-source listing merges.
- [x] Structured product attributes and image references are parsed with shared
      schemas; malformed attributes/media are ignored and cannot raise identity
      confidence or authorize a merge.
- [x] Cross-source comparison requires distinct sources, matched canonical
      identity and corroborating structured brand/model evidence; incomplete
      pairs go to review and conflicts are rejected without mutation.
- [x] Cross-source decisions are pure recommendations with
      `mergeEligible=false`; no listing identity or source record is merged by
      the comparator.
- [x] Persisted cross-source candidates are owner-readable, service-role-written
      and bounded to `MATCH_CANDIDATE`/`REVIEW`; direct authenticated inserts and
      arbitrary-column updates are denied.
- [x] Candidate review uses a fixed-search-path owner-checked RPC and changes
      only `review_status`/`reviewed_at`; acceptance never changes listing or
      source identity.

## F3 — Opportunity valuation

- [x] Valuation inputs and outputs use shared schemas, integer minor units and a
      versioned deterministic formula.
- [x] `opportunity_valuations` has explicit grants, RLS, numeric bounds and
      service-role-only writes; authenticated users receive read-only access.
- [x] Valuation persistence is covered by a live PostgreSQL test after a clean
      migration reset.
- [x] Valuation API reads verify authenticated project ownership and listing
      membership; browser clients never receive write access.
- [x] Scores and maximum purchase prices remain recommendations and do not
      authorize purchase, bidding, payment or other financial execution.
- [x] Persisted price history is read by the server-side collection consumer,
      validated at the Supabase boundary and isolated by listing ID; no browser
      route receives service-role access.
- [x] Optional version/location/shipping/quantity context is Zod-validated
      before valuation; invalid external context fails closed and cannot alter
      the formula through arbitrary payload values.

## F6.1 — Negotiation draft without sending

- [x] Negotiation context and evidence are strict Zod contracts restricted to
      electronics and the three permitted sources.
- [x] An explicit user maximum is required and the deterministic suggestion
      cannot exceed it or the target/asking-price bound.
- [x] Untrusted listing titles and evidence summaries are not interpreted as
      commands; the draft message uses controlled template text and evidence
      references only.
- [x] Output invariants require human review and enforce `sent=false` and
      `executable=false`; `send`, `payment`, `bid`, `command` and `secret`
      fields are rejected by strict schemas.
- [x] No connector, LLM, credential, queue, endpoint or persistence was added;
      tests cover malformed, incomplete, hostile and bounded inputs.
- [ ] Actual seller messaging, follow-up policy, audit persistence and any live
      transport remain separate human-gated work.

## F6.2 — Negotiation draft audit persistence

- [x] The `negotiation_drafts` migration is additive, applies locally, enables
      RLS and has no `SECURITY DEFINER` escape hatch.
- [x] Snapshots are validated by shared strict schemas before parameterized
      persistence; the database also rejects action fields and invalid
      non-sending invariants.
- [x] `authenticated` has owner-scoped SELECT only; `anon` has no access and
      `service_role` is the only writer.
- [x] Live integration tests prove service-role persistence, owner read,
      cross-tenant isolation and authenticated write denial; local security
      advisors report no issues.
- [ ] Retention, deletion/DSAR handling and any message transport remain
      pending separate review and human gates.

## F6.3 — Negotiation context freshness

- [x] Freshness uses only caller-supplied, schema-validated UTC timestamps and
      an explicit bounded age window; it never reads the system clock.
- [x] Missing evidence, invalid windows, future evidence timestamps and stale
      contexts fail closed with `usable=false` and revalidation required.
- [x] The checker is deterministic and has no network, LLM, connector, queue,
      credential or send path.
- [ ] Live revalidation, seller follow-up and any binding action remain
      separate human-gated work.

## F6.4 — Contextual follow-up without sending

- [x] Observed interaction outcomes are strict and bounded; hostile response
      text is treated as data and is not copied into the draft.
- [x] A refusal produces `DO_NOT_FOLLOW_UP` only for the current context and
      cannot create a permanent seller rule.
- [x] Every output requires human review and enforces `sent=false` and
      `executable=false`; no connector, queue, credential or transport exists.
- [ ] Manual message policy, live follow-up and any binding action remain
      separate gates.

## F7.1 — Pending authorization envelope

- [x] Authorization requests are strict, category/source bounded and require
      a safe idempotency key, explicit total-cost limit and expiration.
- [x] Cost is checked as unit price times quantity and cannot exceed the user
      maximum; no payment token, secret, command or transport field is accepted.
- [x] Produced envelopes are `PENDING_HUMAN_APPROVAL`,
      `humanApproved=false` and `executable=false`; the builder has no executor
      or external side effect.
- [ ] Cryptographic signing, replay storage, local authenticated sessions and
      any live purchase/bid/message action remain separate human-gated work.

## F7.2 — Expiration and replay gate

- [x] The gate validates the complete strict envelope and caller-supplied UTC
      timestamp; it does not read the system clock.
- [x] A consumed envelope is `REPLAYED`; otherwise an expired envelope is
      `EXPIRED`; only a valid unused envelope remains
      `AWAITING_HUMAN_APPROVAL`.
- [x] Every result enforces `requiresHumanApproval=true` and
      `executable=false`; there is no executor or external side effect.
- [ ] Persistent replay ledger, cryptographic signing, local session binding
      and any live action remain pending separate review and human gates.

## F7.3 — Persistent authorization ledger

- [x] `authorization_envelope_ledger` is additive, RLS-enabled and constrained
      to validated pending envelopes with no action fields or executable state.
- [x] Idempotency and authorization identity are unique per owner; identical
      retries return the existing record and divergent envelopes fail closed.
- [x] `authenticated` has owner-scoped SELECT only; `anon` cannot read and
      service-role-only adapter methods perform persistence/consumption.
- [x] Live tests cover owner isolation, denied authenticated writes and one
      service-role consumption; local migration list and security advisors pass.
- [ ] Session binding, cryptographic signature, transaction-level executor lock
      and any live action remain separate human-gated work.

## F7.4 — Opaque local session gate

- [x] Session binding accepts only opaque UUID references, never tokens, cookies,
      secrets or credentials; envelope/user identity must match.
- [x] Binding expiration and current-user/current-session mismatch fail closed;
      `SESSION_MATCH` still requires human approval and keeps `executable=false`.
- [x] The gate is deterministic and has no Auth call, network, browser, queue,
      connector or external side effect.
- [ ] Real session validation, revocation checks, cryptographic signing and any
      live executor remain human-gated and intentionally unprovisioned.
